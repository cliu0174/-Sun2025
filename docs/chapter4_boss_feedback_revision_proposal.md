# 第四章老总反馈专项修改建议书

> 本建议书仅针对公司领导反馈形成，独立于此前的技术细节精修建议。核心目标是将第四章从“模型与实验堆叠式写法”调整为“实际 BMS 需求驱动的 SOH 估计方法与验证框架”。

## 1. 修改总目标

第四章应围绕实际电池管理系统中的数据现实展开，而不是直接从模型结构或实验结果切入。建议将全章主线调整为：

> 实际 BMS 中运行数据连续可采集，但容量标定和 SOH 标签往往稀疏、不完整。基于这一工程需求，本文首先选取工况设置较接近实际运行条件的 HUST 公开数据集进行基础模型验证，再结合自建数据集构建部分生命周期监督场景，验证所提出多尺度物理一致性方法在标定受限条件下的 SOH 稳健估计能力，并进一步探索基于预测轨迹的异常风险提示。

该主线强调“需求导向”，即：

1. 实际 BMS 中有什么数据；
2. 实际 BMS 中缺什么标签；
3. 为什么需要部分生命周期监督建模；
4. 为什么选择 HUST 作为公开基线验证；
5. 为什么引入自建数据集作为工程场景验证；
6. 为什么多尺度特征与物理一致性约束服务于这一问题。

## 2. 关键口径调整

### 2.1 删除 CRT 命名

全文不再出现 `CRT` 这一名称，统一改为：

> 自建数据集

第一次出现时可写为：

> 面向实际运行场景采集的自建电池退化数据集

后文统一简称为：

> 自建数据集

不建议使用 `CRT数据集`、`CRT退化数据集`、`CRT-B03` 等命名。若确需区分样本，可改为：

- 自建数据集样本 1；
- 自建数据集典型电池；
- 自建数据集中某代表性电池；
- 代表性测试电池。

### 2.2 标题中减少缩略词

标题中不要堆叠 `BMS`、`SOH`、`CNN`、`LSTM`、`MS`、`PI` 等缩略词。建议标题尽量中文化，最多保留 `SOH` 一个高频专业缩略词。

推荐标题：

> 第四章 基于多尺度特征与物理一致性约束的锂离子电池SOH估计方法

或：

> 第四章 面向部分生命周期监督的锂离子电池健康状态估计方法

不推荐：

> 第四章 面向BMS的MS-PI-CNNLSTM锂离子电池SOH估计与异常识别方法

### 2.3 异常识别降调为工程扩展

异常识别不作为本章主方法标题的一部分，而作为工程扩展内容。建议统一表述为：

> 基于预测轨迹的异常风险提示

不建议写成：

- 完整异常诊断方法；
- 故障诊断模型；
- 异常识别主方法。

推荐口径：

> 该部分并不试图替代专门故障诊断模型，而是利用 SOH 估计模型产生的预测轨迹偏差信号，为实际 BMS 中的异常退化提供低成本风险提示。

## 3. 建议采用的新章节架构

建议第四章按照以下结构重写：

```text
4.1 面向实际BMS的SOH估计问题背景
4.2 部分生命周期监督问题建模
4.3 多尺度物理一致性SOH估计方法
4.4 公开数据集基线验证
4.5 面向工程数据的部分监督验证与分析
4.6 工程扩展：基于预测轨迹的异常风险提示
4.7 本章小结
```

该结构的逻辑是：

> 工程背景 → 问题建模 → 方法设计 → 公开验证 → 工程验证 → 风险提示扩展 → 小结

相比原结构，该安排更符合“理论-验证-工程导向”的要求。

## 4. 各节修改建议

### 4.1 面向实际BMS的SOH估计问题背景

本节需要从实际 BMS 数据现实出发，而不是直接进入模型或数据集介绍。

建议重点说明：

1. 实际 BMS 中可连续采集的数据包括电压、电流、温度、时间、充放电过程记录等；
2. 真实容量和 SOH 标签通常需要周期性容量测试或离线诊断，难以连续获得；
3. 因此实际工程中存在“运行特征连续可得、健康状态标签稀疏可得”的矛盾；
4. 传统完整生命周期监督假设与实际部署条件存在差距；
5. 本文方法正是针对这一标定不完整问题展开。

推荐加入核心表述：

> 在实际电池管理系统中，电压、电流、温度和时间等运行数据通常能够随充放电过程连续采集，而真实容量和 SOH 标签往往依赖周期性容量测试或离线标定，难以在完整生命周期内连续获得。因此，SOH 估计模型不仅需要具备跨电池泛化能力，还需要能够在标签稀疏、不连续的条件下稳定利用完整运行轨迹信息。

本节还应解释为什么选 HUST：

> HUST 公开数据集包含统一充电协议、多阶段放电工况和完整生命周期容量记录，其工况设置能够较好反映实际运行中负载变化带来的退化差异，因此适合作为公开基准数据集，用于验证模型在相对接近实际运行条件下的基础 SOH 估计能力与跨电池泛化能力。

### 4.2 部分生命周期监督问题建模

本节承担“理论建模”功能，不宜写成普通数据处理说明。

建议保留：

- 部分生命周期监督的定义；
- Label Masking 思想；
- 有标签循环和无标签循环的区别；
- 为什么无标签循环不能直接删除；
- 物理约束为什么能在无标签区间提供结构性信号。

建议减少：

- 具体标准化流程；
- 异常值清洗细节；
- 训练/验证/测试划分比例；
- 过多数据集描述。

这些细节可放入 `4.4` 或 `4.5` 的实验设置中。

推荐本节核心表述：

> 部分生命周期监督并非简单减少训练样本，而是在保留完整运行特征轨迹的同时，仅屏蔽缺失 SOH 标注循环的数据误差项。这样既避免了删除无标签循环导致的退化序列断裂，又为物理一致性约束在无标签区间发挥结构性弱监督作用提供了条件。

### 4.3 多尺度物理一致性SOH估计方法

本节作为方法主体，建议突出两个核心设计：

1. 多尺度特征提取；
2. 物理一致性弱监督约束。

标题中不建议直接出现 `MS-PI-CNNLSTM`。模型缩写可以在正文首次定义后使用。

建议写法：

> 本文提出一种基于多尺度特征提取与物理一致性约束的 SOH 估计模型。该模型首先通过不同感受野的卷积结构提取局部响应、阶段趋势和长期退化信息，再利用循环神经网络建模跨循环状态演化，最后在损失函数中引入软单调物理约束，使无标签生命周期区间也能够通过退化方向先验参与模型训练。

本节建议强调：

- 多尺度特征提取服务于有限标签条件下的表征能力；
- LSTM 服务于跨循环状态演化；
- 软单调约束服务于无标签区间的结构性弱监督；
- 方法设计来自 BMS 数据现实，而不是单纯追求网络复杂度。

### 4.4 公开数据集基线验证

本节建议专门放 HUST 公开数据集相关实验。

建议说明：

1. HUST 作为公开数据集，主要用于公开可比性和基础能力验证；
2. HUST 工况与实际运行需求具有一定相似性，如多阶段放电、跨电池差异、完整生命周期退化；
3. 在 HUST 上验证模型不是只对自建数据有效；
4. 本节可放完整监督基准、公开数据集消融和跨电池泛化结果。

推荐表述：

> 为避免仅在自建数据上验证导致结论缺乏公开可比性，本文首先选取 HUST 公开数据集作为基线验证平台。该数据集具有完整生命周期容量记录和多阶段放电工况，能够用于检验模型在公开基准条件下的基础估计能力、跨电池泛化能力以及多尺度结构的有效性。

本节可包括：

- HUST 数据集简介；
- 公开数据集特征提取；
- 电池级划分；
- 对比模型；
- 完整监督结果；
- 多尺度结构消融。

### 4.5 面向工程数据的部分监督验证与分析

本节建议专门放自建数据集和部分生命周期监督验证。

核心作用是承接 4.1 的 BMS 数据现实：

> 公开数据集验证基础能力，自建数据集验证工程标定受限场景。

建议说明：

1. 自建数据集来自面向实际运行场景的采集过程；
2. 自建数据集用于构建 SOH 标签稀疏、不完整的工程验证场景；
3. 保留完整运行特征轨迹，仅对部分循环提供 SOH 标签；
4. 比较不同监督比例下模型性能；
5. 重点分析物理一致性约束在低标签条件下的价值。

推荐表述：

> 在完成公开数据集基线验证后，本文进一步结合自建数据集构建更接近实际 BMS 标定条件的部分生命周期监督场景。与完整监督不同，该场景假设运行特征可以连续获得，而 SOH 标签仅在部分生命周期区间可用。该设置用于检验模型在工程标定受限条件下是否仍能维持稳定的 SOH 估计能力。

本节要特别强调：

- HUST 是公开基线验证；
- 自建数据集是工程场景验证；
- 二者不是简单并列，而是承担不同验证功能。

### 4.6 工程扩展：基于预测轨迹的异常风险提示

本节建议作为工程导向扩展，不作为本章主贡献。

建议核心逻辑：

1. 实际 BMS 中不仅需要 SOH 估计，也需要对异常退化形成早期提示；
2. 已训练 SOH 模型的预测轨迹包含退化状态信息；
3. 当电池进入异常退化模式时，预测轨迹可能偏离正常平滑趋势；
4. 因此可利用轨迹偏差构造低成本异常风险提示信号。

推荐表述：

> 在实际应用中，SOH 估计结果不仅可用于健康状态评估，也可为异常退化风险提示提供辅助信息。本文在不额外训练故障诊断模型的前提下，基于已训练 SOH 模型输出的预测轨迹构造偏差信号，用于识别突发老化、容量拐点和析锂台阶突降等具有明显轨迹扰动特征的异常场景。

注意边界：

- 对突发型异常可强调效果；
- 对渐进型异常要承认难度；
- 不要写成完整诊断系统；
- 不要把异常识别放入章标题。

### 4.7 本章小结

小结建议围绕“需求-方法-验证-工程扩展”回扣。

建议包括四点：

1. 从实际 BMS 数据现实出发，明确 SOH 标签稀疏和部分生命周期监督问题；
2. 提出多尺度物理一致性 SOH 估计方法；
3. 通过 HUST 公开数据集验证基础估计能力和跨电池泛化；
4. 通过自建数据集验证工程标定受限场景，并探索预测轨迹异常风险提示。

推荐结尾表述：

> 本章的核心并非单纯追求模型结构复杂化，而是围绕实际 BMS 中运行数据连续、SOH 标定稀疏的工程矛盾，构建从问题建模、方法设计到公开验证和工程验证的完整技术路线。

## 5. 关于“数据处理是否放到实验章节”的建议

公司领导建议将数据处理放到实验章节。总体上，这一建议合理，但需要拆分处理。

### 5.1 应保留在方法/问题建模部分的内容

以下内容不应完全移到实验章节：

- 实际 BMS 数据现实；
- SOH 标签不完整问题；
- 部分生命周期监督定义；
- Label Masking 机制；
- 保留无标签循环特征的原因；
- 物理约束在无标签区间提供弱监督的机制。

这些属于问题建模和方法逻辑，是第四章主线的一部分。

### 5.2 可放入实验验证部分的内容

以下内容适合放入 `4.4` 或 `4.5`：

- HUST 数据集具体参数；
- 自建数据集采集说明；
- 特征提取流程；
- 异常值清洗；
- 标准化；
- 训练/验证/测试划分；
- 监督比例设置；
- 对比模型；
- 训练超参数；
- 评价指标。

建议处理原则：

> 方法部分讲“为什么这样建模”，实验部分讲“具体怎样处理数据并验证”。

## 7. 推荐修改顺序

建议按照以下顺序推进：

1. 全文替换 `CRT` 为“自建数据集”，同步调整样本命名。
2. 调整第四章标题，减少缩略词堆叠。
3. 按 `4.1-4.7` 新结构重排内容。
4. 重写 `4.1`，突出实际 BMS 数据现实和 HUST 选择原因。
5. 将原 `4.2` 中的数据处理细节拆分：问题建模留在 `4.2`，具体处理移到 `4.4/4.5`。
6. 精简 `4.3`，突出多尺度特征和物理一致性弱监督，不再强调复杂模块堆叠。
7. 将 HUST 结果集中到 `4.4`，作为公开数据集基线验证。
8. 将自建数据集和部分监督实验集中到 `4.5`。
9. 将异常识别降调为 `4.6` 工程扩展。
10. 重写 `4.7`，按需求、方法、公开验证、工程验证、扩展应用总结。

## 8. 总结

本轮修改的核心不是技术细节微调，而是论文叙事方式重构。建议将第四章从“模型方法和实验结果汇总”调整为：

> 从实际 BMS 数据现实出发，以公开 HUST 数据集完成基础验证，以自建数据集完成工程标定受限场景验证，以多尺度特征和物理一致性约束支撑部分生命周期监督下的 SOH 稳健估计。

这样修改后，第四章将更符合公司领导提出的“理论-验证-工程导向”要求，也更容易在论文答辩和工程项目汇报中解释清楚方法来源、验证路径和应用价值。
